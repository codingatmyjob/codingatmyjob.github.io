Git Essentials

Git has a lot of commands, but most day-to-day work comes down to checking what changed, choosing what to save, and keeping your branch in sync. These are the commands I come back to most. Run them from your repository, and swap placeholders like <branch> and <file> for your own names.

Commands I Use Often

I usually start by checking the working tree, then inspect the exact changes before staging anything.

git status -sb                 # Short status, including branch
git switch <branch>            # Switch to an existing branch
git switch -c <branch>         # Create and switch to a new branch
git log --oneline --graph --decorate -12  # Read recent history as a graph
git diff                       # See unstaged changes
git diff --staged              # See changes selected for the next commit
  • When I come back to a project, git status -sb quickly reminds me which branch I'm on and what I've changed.
  • I use git switch to move between branches. You may still see git checkout in older guides; it can switch branches too, but it also handles other operations.
  • git diff shows edits that are not staged yet; git diff --staged lets me check what the next commit will actually contain.

Everyday Commands

Stage and Commit
git add <file>                 # Stage one file
git add -p                     # Select individual change hunks
git add -A                     # Stage all additions, edits, and deletions
git commit -m "Describe change" # Save staged changes as a commit
  • If I've been working on a few things at once, I stage only the files for this change. With git add -p, I can even pick individual hunks from one file.
  • When everything belongs in the same commit, git add -A stages all additions, edits, and deletions. I still check git diff --staged before saving it.
  • Git commits the staged snapshot, not every edit on disk. Anything I leave unstaged stays in my working tree for later.
Branches and Remotes
git branch                     # List local branches
git fetch                      # Download remote updates without merging
git pull                       # Fetch and integrate the current branch's upstream
git push                       # Publish commits to the configured upstream
git push -u origin HEAD        # Publish this branch and set its upstream
  • git fetch is a good way to see what changed on the remote without changing my current files or branch.
  • git pull brings the upstream branch into the branch I'm on. I check my status first, then handle any conflicts Git reports.
  • The first time I publish a new branch, git push -u origin HEAD sets its upstream too. After that, plain git push is usually enough.

Undo Carefully

Git has a few different kinds of “undo,” and they are not interchangeable. I check git status first so I know whether I'm changing the staged snapshot, my local files, or commit history.

git restore --staged <file>    # Unstage; keep edits in the file
git restore <file>             # Discard unstaged edits to the file
git revert <commit>            # Add a new commit that reverses an older commit
git commit --amend             # Replace the latest local commit
  • Staged the wrong thing? git restore --staged takes it out of the next commit but leaves the edits in the file.
  • git restore <file> discards that file's unstaged edits. I look at the diff first, because Git won't normally be able to bring those edits back.
  • For a commit I've already shared, git revert is usually the right tool: it adds a new commit that undoes the earlier one without rewriting history.
  • git commit --amend replaces the latest commit. I use it to fix a local commit, not one I've already pushed, unless the team has agreed to rewrite shared history.

Stash Temporary Work

git stash push -m "work in progress"  # Save tracked edits temporarily
git stash list                         # List saved stashes
git stash pop                          # Reapply latest stash and remove it
git stash apply                        # Reapply latest stash and keep it

When I need to switch branches but my current work isn't ready for a commit, I stash it temporarily. A normal stash saves tracked-file changes; add -u for untracked files too. I use apply when I want to keep the saved copy around until I've checked that everything came back correctly.

Combined Workflows

Start a Feature Branch
git switch main && git pull && git switch -c feature/my-change

I start from an up-to-date base branch so the new work doesn't begin behind its upstream. The && means each command runs only if the previous one succeeds.

Review, Commit, and Publish
git status -sb && git diff && git add -p && git diff --staged && git commit -m "Add my change" && git push -u origin HEAD

This is the full loop I use when I'm ready to share a change: inspect, stage only what belongs, review the staged snapshot, commit, and publish the branch. If a command fails, && stops the chain there.

When I'm unsure what to do next, I go back to the same loop: check status, make a focused change, review it, stage intentionally, check the staged diff, then commit and push.
