How Fit Am I? Compare Your Race Times

November 20, 20269 min read
Demo Data Science WebApp Python

Introduction

I've been MIA for a few months, but I'm currently in the process of building an undisclosed full stack webapp that helps runners track their training, understand their progress, and prepare for their next race. It currently features a training plan builder, weekly personalized workouts, logs their stats, a race result comparison tool, and more. This is a pretty daunting task for me, as I've never attempted anything quite this large before. I started clearly scoped and defined, and I have slowly added more features, algorithms, and improvements over time. Scope creep is the worst.

This article is going to drill down into the science and reasoning behind one specific tool called "How Fit am I". "How Fit am I" enables a user to see where their race times would fall compared to the broader running population. The feature compares race results in similar distance, age, and gender groups. Its comparison logic in the webapp is written primarily in Python, and I'll show the relevant code further down in the article.

Constraints and Considerations

At the webapp's core, the user can ingest their activity data from a connected fitness platform. Naturally, the easy approach to this would be to leverage the collected activity data from the connected platform, and compare the input data against other connected user's data. This is where reading terms and conditions when connecting to a third party API becomes crucial. The API's developer rules strictly limit data visibility to the athlete who authorized it and prohibit aggregating that data for analytics. That ruled out pooling users' activity histories into a shared benchmark, so I began looking for race results instead.

Kaggle was my obvious first stop; it's a catalog for exploring large public datasets, but I could not find a dataset with the race distances and age-and-gender coverage I needed. With that in mind, I turned to other sources. A large marathon-results dataset on GitHub gave me a starting point for marathons. Here's where I began to struggle.

I had to find and manually collect public results from other sources for the remaining distances (5K, 10K, half marathon). Not many race result websites are forthcoming with user data, so collecting a comprehensive dataset required significant manual effort (almost a full day copying and sanitizing data to remove PII). After standardizing rows, the reference file contained a whopping 809,781 race results.

Now as a coworker would say: "It's time to science up the data." Loading and parsing all of those rows in a browser would be inefficient and slower than the average user would like, so I built a compact reference table. Try the comparison first; below it, I'll walk through how the data becomes a searchable reference table.

From 809,781 Results to a 54 KB Lookup Table

I didn't want to make the website load and sort every race result whenever someone entered a time. Instead, I turned the results into a smaller reference that could still make a useful comparison. Here's how I organized the data and what each step accomplishes:

  1. Put ages into consistent ranges
    Race results don't all record ages the same way. Some list an exact age, while others provide only an age range (e.g., 30-34). I put exact ages into five-year bands, with under-20 and 70-plus groups at the ends. When a source's age range is too broad (e.g., 20-39) to fit confidently into one band, I leave it out instead of guessing where to place it.
  2. Compare similar runners
    I group results by distance, gender, and age band, so a 5K result is not compared with a marathon, or one age range with another. Across four distances, two genders, and twelve age bands, there are 96 possible comparison groups.
  3. Keep one large event from dominating
    Some events contribute far more results than others, so I count each event's finishers by distance, pooling results across years. If an event has 5,000 finishers or fewer, each result counts once. If it has more, each result counts as a smaller share: for example, with 20,000 finishers, each counts as 0.25. Across all of that event's age and gender groups combined, those results then contribute 5,000 weighted results instead of 20,000. Put another way, each finisher adds 0.25 rather than 1 to the running total used to set percentile cutoffs. The finish times stay unchanged and no results are removed.
  4. Save the percentile benchmarks
    For each group, I sort finish times and save a time cutoff for every represented percentile; 1 through 100. When someone uses the tool, the site checks their time against those saved cutoffs instead of sorting the full set of results again.

The app's final reference is a 54,754-byte JSON file: 96 comparison groups with 100 thresholds each, or 9,600 threshold values in total. That's about 71 times smaller than the standardized Parquet input with 809,781 rows. Each group also keeps its raw finisher count, so the app can show how many results fed into the comparison.

What a Percentile Means

For a selected distance, age band, and gender group, the app finds the highest stored cutoff that the time beats. An 80th-percentile result means the time is faster than about 80% of the event-weighted comparison, and is best read as a comparison bucket. It provides broad context for a race result, not a universal measure of running ability.

How a Lookup Becomes a Percentile

First, I keep a large event from counting as if every finisher had the same influence. If an event has 20,000 finishers, each result keeps its actual time but adds only 0.25 to the tally used to build the percentile cutoffs. Together, those results count as 5,000 finishers instead of 20,000. I attach that share to each result and keep it with the result's distance, gender, and age group: 

event_weight = min(1.0, 5_000 / event_size)
group_key = (distance, gender, age_band)
groups[group_key].append((finish_seconds, event_weight))

Next, I sort each group from slowest time to fastest and move through it once. Each finisher adds their share to a running total. When that total reaches the mark for a percentile, I save that finisher's time as the cutoff for that percentile. The code below creates one cutoff for each percentile from 1 through 100: 

results.sort(key=lambda item: -item[0])
total_weight = sum(weight for _, weight in results)
cutoffs, cumulative, index = [], 0.0, 0

for percent in range(1, 101):
    target = total_weight * percent / 100 - 1e-9 * total_weight
    while cumulative < target and index < len(results):
        cumulative += results[index][1]
        index += 1
    cutoffs.append(results[index - 1][0])

Once I have the cutoffs, the lookup is much simpler. When someone enters a time, the site uses their age to find the right age band, then selects the group for their distance and gender. It checks the cutoffs from the 1st percentile upward, counting the ones the time is faster than. If the time ties a cutoff, it doesn't count as faster. The original results don't need to be sorted again: 

if age < 20:
    band = "U-20"
elif age >= 70:
    band = "70+"
else:
    start = age // 5 * 5
    band = f"{start}-{start + 4}"

group = groups.get(race, {}).get(sex, {}).get(band)
percentile = 0
for level, threshold in enumerate(group["thresholds"], 1):
    if threshold <= seconds:
        break
    percentile = level

Caveats

  • The score largely depends on the available race results, and on how those results are grouped and weighted. This was an issue I ran into with using a Marathon with a qualifying time cutoff time as a reference, since it excluded more of the slower finishers and skewed the overall comparison.
  • The score serves as a reference point, not a measure of fitness or ability.
