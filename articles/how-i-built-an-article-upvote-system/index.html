How I Built an Article Upvote System

November 24, 2026 · 5 min read
NotesCloudflareSQLJavaScriptAPI

Overview

As Tangent continues to grow, I've been looking for ways to add functionality without introducing unnecessary complexity. One of the latest additions is an article upvote system that lets visitors provide feedback and gives me another way to gauge content engagement.

Like I've said before in other articles, I want to keep Tangent architecturally simple, and I want to keep it as close to free as possible. Rather than introducing a full new backend for voting, I implemented a small API using a Cloudflare Worker. D1 handles vote storage and aggregation.

The result is a lightweight voting system with no additional hosting costs. Below I'll cover the architecture, database structure, API, and some of the limitations.

Why add voting at all?

I've reached a point where I'm trying to "feature-maxx" Tangent without overcomplicating the UI or underlying architecture. I want the portfolio to have its own identity, stand out in the sea of project portfolios, and give visitors more ways to interact with content.

An upvote system seemed like a good fit. It doesn't interrupt the user experience, and provides a simple metric for identifying which articles visitors find useful.

Cost

The entire voting system fits within Cloudflare's free-tier allowances, so the current hosting cost is $0. Below is a breakdown of the free and paid tiers for Workers and D1:

  • Workers Free: 100,000 requests/day and 10 ms CPU per invocation.
  • D1 Free: 5 million rows read/day, 100,000 written/day, and 5 GB storage.
  • Workers Paid: Starts at $5/month, including 10 million requests and 30 million CPU milliseconds.
  • D1 Paid: Includes 25 billion reads/month, 50 million writes/month, and 5 GB storage.

Tangent's voting Worker is configured for 120 reads and 10 writes per minute per IP. These limits are approximate and applied per Cloudflare location rather than globally. For a static portfolio, these allowances are more than enough.

Architecture

The implementation consists of three components: the browser, a Cloudflare Worker, and a D1 database. Astro generates the static pages, browser-side JavaScript handles vote counts and requests, and the Worker validates requests and coordinates database operations. D1 stores individual votes. The browser never actually touches D1 directly.

Database Schema

Rather than maintaining a separate counter for each article, I store one row per article and voter ID. The total number of rows associated with an article's slug determines its vote count. 

CREATE TABLE helpful_votes (
  slug TEXT NOT NULL,
  voter_id TEXT NOT NULL,
  PRIMARY KEY (slug, voter_id)
) WITHOUT ROWID;

Each visitor receives a generated voter ID stored in browser local storage, which the Worker uses to identify their votes. I don't store or collect any identifiable information. Clearing browser storage can generate a new ID, so this isn't strict identity verification.

Worker API

The Worker supports two GET behaviors and one POST endpoint:

  • GET /votes?slug=... returns the count for a specific article.
  • GET /votes returns totals for all articles, grouped by slug.
  • POST /votes submits a vote using an article slug and voter ID.

The Worker validates the request origin, article slug, and voter ID before querying D1. The insert uses an ON CONFLICT clause to prevent duplicate votes: 

const insert = env.DB.prepare(
  'INSERT INTO helpful_votes (slug, voter_id) VALUES (?, ?) ON CONFLICT (slug, voter_id) DO NOTHING'
).bind(slug, voterId)

The insert and updated count are executed together in a D1 batch. This eliminates the need for a separate counter and keeps vote aggregation straightforward.

Security in Mind

The Worker validates known article slugs, request methods, and voter ID formats. It also uses parameterized SQL statements and separate IP-based rate limits for reads and writes.

The configured origin check provides a CORS restriction, not authentication. It doesn't prevent direct API requests or guarantee that a visitor only votes once. Client-side voter IDs can also be regenerated by clearing local storage.

Next Steps

For now, votes give readers a way to show interest. If they prove useful, and if I collect enough data, I think I can use the vote metrics to automatically inform and determine future highlighted articles.
